## Animation and overhead

Destination-only status/navigation/taskbar snapshots now become part of the
existing animation's input texture. The normal projection, motion, glass,
blur pyramid, fades and selected output resolution apply to that texture.
This replaces that mode's after-effect bar painting. Native exposure and
per-screen cached mode retain their separate comparison behavior.

A single worker bakes the current destination's cropped pixels over the retained
app image at the existing capture resolution, then creates the seven blur levels.
The resulting texture is reused across animation frames. Existing guarded app
captures that already contain the same bar pixels require no composition. No
per-frame screenshots, bitmap allocations or mip builds are introduced. Work is
coalesced across sessions; obsolete/unpublished results are recycled. Published
images are left to normal lifetime management because a GPU submission may still
reference them. Reports include composition count/time and image-vs-metadata
capture counts; these are software timings, not total GPU or handset overhead.

The cosmetic frame never replaces the app-readiness frame or changes native
handoff gates. Exact physical identity, dimensions and rotation are required;
a source placeholder cannot receive destination bars. No cross-panel stretching
or source-bar fallback is restored.

Snapshot discovery remains bounded to 12 attempts per physical primary with a
250 ms cooldown. Each native window/geometry signature gets an initial image
and one settling refresh. Subsequent checks with the same signature inspect
metadata without taking a screenshot. Newly appearing taskbar geometry gets
fresh images. Window tokens, bounds, physical ID, dimensions and rotation all
participate in the signature. Pixel content can change without a geometry
change, so this is deliberately a visual snapshot, not a live taskbar feed.

## Inner taskbar investigation

The previous parser rejected full-screen taskbar containers and floating
bottom taskbar frames; it also missed `TaskbarWindow` titles. These are concrete
capture limitations, but the supplied Samsung report does not establish which
one causes this handset's missing taskbar.

- Recognize Taskbar/TaskbarWindow titles with optional numeric suffixes, while
  still requiring the corresponding privileged navigation window types.
- Accept bounded floating taskbar frames in the bottom quarter of the display.
- For full-screen taskbar/navigation containers, accept only the OS's explicit
  global touchable rectangles in that bottom quarter, with ready region insets.
  Reject full-screen, out-of-bounds, central, malformed or pending regions.
  Never guess a strip height or capture the entire taskbar container.
- Require drawn/shown/ready state and stable window tokens and bounds before and
  after capture. Union overlapping regions to avoid painting them twice.
- Preserve uncovered taskbar pixels from the same unfolding session when a
  later capture contains only the status bar or gesture handle. New pixels
  overwrite overlaps; nothing is imported from another panel/session in this mode.
- Report candidate names, readiness, bounds, accepted region counts and region
  source even when a status capture succeeds. Distinguish no named taskbar,
  hidden/not-drawn state, pending insets and no bounded drawn region.

AOSP demonstrates why frame size alone is insufficient: Launcher3 can make its
[taskbar window full-screen](https://android.googlesource.com/platform/packages/apps/Launcher3/+/323368eb4f/quickstep/src/com/android/launcher3/taskbar/TaskbarActivityContext.java),
and [WindowState](https://android.googlesource.com/platform/frameworks/base/+/24311a64742c81b4ee5399e6785695d7c772334a/services/core/java/com/android/server/wm/WindowState.java)
prints its computed touchable region in global coordinates. Samsung may use a
different window layout. Touchable bounds and HAS_DRAWN do not prove icon pixels.

This change captures native taskbar content when Android supplies it; it does
not create Samsung's taskbar on D1, alter focus/decor policy, or delay handoff to
wait for it. The documented firmware constraints still apply. If Android creates
it only after native handoff, its appearance can still be late. The next handset
report should distinguish that case from rejected capture geometry.

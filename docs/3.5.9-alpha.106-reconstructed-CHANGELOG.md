# Alpha.106 reconstructed local — incoming image preparation

VersionCode 1359. Baseline: alpha.105, commit
de9638ee8a85fe8e4dfbfe7fa4271028cb3e8d3b.

## Report and cause

The user confirms alpha.105 works except for the incoming display retaining its
frosted preview. Current alpha.105 sessions 12511595, 12521635 and 12528807 fail
brightness preparation after roughly two seconds, each missing the incoming
physical panel's restored command. BRIGHTNESS_BLOCKED prevents task movement
and primary switching, so destination capture never starts. In session 12528807
the inner renderer has zero native-texture frames while held at 132 degrees.
The genuine pause later remaps the task and dissolves the preview. This is a
preparation veto, not a measured rendering-rate or thermal failure.

The successful control session 12518155 gets brightness at +643 ms, begins the
primary request around 20 degrees, accepts an inner app capture at +1099 ms,
and completes handoff around +1218 ms, before the 175-degree endpoint. The
existing capture/render path can therefore supply the incoming image mid-fold.
Historical alpha.103/104 records and idle screen-off periods are not treated as
evidence for this current issue.

The previous refresh targets only physical panels missing a command. A missing
incoming panel maps to logical D1. In Android concurrent-display brightness
policy, the follower strategy precedes the temporary-brightness strategy: a
temporary adjustment on the follower may be ignored. Clearing that ineffective
adjustment then gives no new hardware command to satisfy the restore gate.
This is a source-supported explanation consistent with the handset pattern,
not a direct observation of Samsung's internal selected brightness strategy.

Reference (strategy-selection order):
https://android.googlesource.com/platform/frameworks/base/+/0d29f42497f93df5e09d5a2180afd8226f8eefca/services/core/java/com/android/server/display/brightness/DisplayBrightnessStrategySelector.java

## Narrow correction

Live B8 uses a separate LiveB8BrightnessRefresh helper. If either physical
sample is missing, it refreshes the current primary, logical D0, once. It uses
the existing small 1/255 temporary adjustment, 180 ms duration, NaN clear back
to automatic/manual policy, 250 ms settling interval and independent six-second
cleanup watchdog. It does not change saved brightness or brightness mode.
The physical identities of both ON panels must remain stable around the refresh.

Because the primary adjustment can affect its follower, BOTH physical panels
now require their own valid post-clear SurfaceFlinger commands. The old primary
sample cannot authorize a hold after the refresh. No brightness or nits value
is copied between displays, manufactured, or taken from a pre-clear probe.
The existing bounded command observation, SDR validation and physical writer
are retained. Restoration failure still uses alpha.105's motion-preserving
blocked-handoff behavior. App brightness overrides or a vendor policy that
ignores the primary refresh may still prevent preparation; this is not a
permission to switch using unvalidated values.

LiveB8Controller, renderer, capture pipeline, rotation, power, hinge thresholds,
1.5-second stillness timer, pause unwind/dissolve and endpoints are unchanged.
The original BrightnessRefresh and PhysicalBrightnessHold used by the Lab
checkpoint are unchanged. Apart from build identity, production changes are
limited to LiveB8Brightness and its new refresh helper.

## Validation

Run tools/check_live_b8.py. The new real-helper harness models Android's
primary/follower precedence, reproduces an incoming-only refresh producing no
commands, and checks primary-driven restoration in both physical directions,
with either/both samples missing. It verifies distinct per-panel values,
post-clear boundaries, bounded probing, cancellation, mapping/power changes,
invalid values, cleanup failure and the independent cleanup journal. The real
brightness-preparation harness rejects a stale outgoing sample after the pair
refresh. Existing controller, stream, scene, task, power and cleanup tests run.
The delivery build uses tools/build_local_test.py with committed source and
executes the full JVM suite before packaging APK, source history and hashes.

No connected SM-F971U or optical measurement is available. On-device validation:
fold and unfold the same app, lingering on the incoming screen before the
endpoint. The expected trace is PRIMARY_PAIR_REFRESH, RESTORE_COMMANDS_READY,
TASK_MOVE_BEGIN/PRIMARY_REQUEST and DESTINATION, with nativeTextureFrames
increasing during the fold. Check Home as well. Retain the user's existing
settings. Software commands, captures and commits do not prove visible pixels.

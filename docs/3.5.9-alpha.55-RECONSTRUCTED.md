# 3.5.9-alpha.55-reconstructed — earlier Home preparation and cover frost

Recovery target remains alpha.20. This is reconstructed source, not a claim of
original-source equivalence. The user confirmed alpha.54's full-width inner
Home frost worked, then requested earlier native Home in both directions and
the same treatment for the inner-image placeholder on the cover.

## Scope and behavior

- HOME activity type only. Ordinary app folding/unfolding retains its previous
  capture path, shader, primary thresholds, readiness and cleanup behavior.
- On each Home session's first primary transfer, request the destination at the
  saved handoff angle. With the saved 85-degree angle this means opening at 85
  instead of 105 and closing at 85 instead of 65. Both committed presentations,
  brightness preparation and the existing input/lock/lease checks are still
  required. This gives Android's destination launcher layout a 20-degree head
  start; it does not assert that Samsung finishes within any fixed time.
- Once that first request is made, Home uses the existing +/-20-degree hold
  band for subsequent reversals in the same session. Jitter near the saved
  angle must not repeatedly remap the primary. Home roots are never moved.
- The source Home image now supplies a full-panel coarse frosted placeholder
  on either destination: cover-to-inner on opening and inner-to-cover on closing.
  The source panel's own native image is not veiled. Once the validated native
  destination image arrives, dissolve into the unchanged current-angle renderer
  over 120 ms (previously 180 ms). Endpoint release never waits for the effect.
- Rejected/missing native content remains covered; elapsed time never promotes
  a faded/empty launcher capture. No new captures are made for the blur.

## Home capture scheduling

Previously the global 350 ms cooldown began before the shell Home guard, even
if that guard rejected and no screenshot request was issued. Such a failure
could leave most of a cooldown before the next useful check. The cooldown is
now charged at the screenshot request attempt; a preflight failure can retry
after 50 ms. Requests remain single-flight, with an 800 ms callback bound and
late-buffer disposal.

Screenshot pacing is keyed by the accessibility window ID and measured with
uptime, with a 350 ms floor between attempts on the same window. A physical
panel remap does not reset that window's cooldown. A recreated launcher window
can prepare immediately. An Android interval error starts another full cooldown
from the error response. The caller uses the remaining delay directly instead
of retrying through the generic app-capture delay.

This follows AOSP's per-window request interval (333 ms, plus our margin):
https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/AbstractAccessibilityServiceConnection.java

The before/after shell Home guard, focused-window identity/bounds, exact physical
mapping/dimensions/rotation and launcher-alpha checks remain. The second guard
now runs before bitmap readback, avoiding that work when a buffer is already
invalid. Accepted pixel quality, mip resolution and wallpaper-behind-launcher
composition are unchanged. Shared app capture code and shared shader are not
modified.

## Evidence and validation

`HOME_PREP_EARLY` marks the first Home-only request. `HOME_CAPTURE_TIMING` records
physical panel, task/window, whether a screenshot was requested/accepted, queue,
preflight, screenshot, post-capture validation, bitmap build, worker and main
delivery durations, and the next retry delay. A stage value of -1 is unmeasured,
not zero latency. Existing diagnostics distinguish the frosted preview from a
native-panel image. These are software times, not optical or touch latency.

- 509 unit tests pass, including both directions/rotations of Home-only frost,
  the 120 ms dissolve and endpoint shortcut, unchanged missing/faded-image
  rejection, and six capture-pacing tests.
- 454 deterministic checks execute the production B8 controller, including
  earlier Home preparation in both directions, unchanged app thresholds,
  repeated angle jitter, deliberate reversal, brightness blocking, and missing
  native image/window evidence. Existing cleanup, brightness (25), scene (19)
  and task-routing (24) checks pass.
- Final delivery uses a clean committed source build and compatible test APK
  signing, with complete source/history and a hash manifest.

No handset is connected here. Actual visible speed and glitch-free behavior
remain to be checked on the SM-F971U. Compare slow and fast Home folds in both
directions, pause near the saved angle, and reverse across it. The native layout
still depends on Samsung remapping and drawing Home; no readiness gate was
removed to make a screenshot appear sooner. Ordinary apps are a regression
check, not a retuning target.

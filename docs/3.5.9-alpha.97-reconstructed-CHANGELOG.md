# 3.5.9-alpha.97-reconstructed

Duo responsiveness pass based on the SM-F971U Android 17 alpha.96 comparison.

## Evidence and limits

The report contains four normal Live Screen folds at elapsed 919100471 through
919114216, followed by Duo sessions 919115772, 919118503, 919121063 and 919123486.
The routes establish the switch; the report does not contain a matched optical
FPS benchmark. The legacy renderer's retained 64.4/58.2 submitted-fps samples
cannot be assigned to a specific fold or treated as panel refresh measurements.

Duo's source-image completion callbacks arrive 179, 200, 192 and 234 ms after
app-side session setup. Matching destination-image callbacks arrive at 1410 ms,
not before endpoint, 1269 ms and 1273 ms respectively. The last fold reports
277/246 ms maximum moving draw gaps. Capture retries reject competing task 22048
and faded app images; their correctness guards remain required. Both routes
show remap stalls. Live Screen window READY observations 17–35 ms after remap
are not equivalent to Duo's destination-image completion or optical readiness.

## Changes

- Screen-on Duo endpoints use a 32 ms polling target instead of backing off to
  100 ms. Active sessions retain 16 ms and screen-off retains its independent
  500 ms cadence. Closed-hinge rejection and jitter thresholds are unchanged.
- Direct physical renderers pace the next frame from transaction latch, rather
  than serializing every new GPU draw behind presentation completion. At most
  two frames await completion; only one GPU submission awaits latch. The same
  three-buffer ceiling and signaled compositor release fences govern reuse.
- Completion continues to supply handoff evidence. Each callback carries its
  submitted pose and geometry epoch, out-of-order callbacks cannot regress
  evidence, and the watchdog tracks the oldest outstanding frame. Closing the
  scene suppresses late latch and completion callbacks.
- Ordinary-app brightness reads begin during secondary-panel wake and source
  capture. Missing-sample brightness refresh still requires the controller's
  both-ON gate, is bounded, and stops on cancellation. Subsequent legs retain
  independent preparation; native Home/workspace preparation is unchanged.
- Reports include submitted-frame count, latch delay and bounded in-flight
  count. A missing previous commit is now reported as -1 rather than an uptime-
  sized frame gap.

Live Screen rendering, smoothing, effect resolution, glass appearance, capture
opacity/task guards, rotation proof, task move/request ordering and native
endpoint readiness requirements are unchanged. This does not address or claim
to prevent Samsung's earlier system_server BLASTSyncEngine failure.

Android's callback distinction and release-fence contract:
https://developer.android.com/reference/android/view/SurfaceControl.Transaction

## Validation

- 722 JVM unit tests passed before the delivery build, including pipeline
  overlap, queue bounds, reordered/duplicate callbacks and watchdog age.
- Production renderer with fake GPU/compositor: 43 lifecycle checks, including
  latch-before-completion overlap, distinct buffers and late-callback cleanup.
- Controller: 1024 lifecycle/readiness checks; brightness: 81; scene: 28;
  task routing: 70; power: 19; shield cleanup checks passed.
- Delivery uses the clean committed source via tools/build_local_test.py.

No handset is connected. Actual frame rate, visible startup, power consumption
and improvement relative to Live Screen require a device test. In particular,
geometry/remap waits and guarded destination-capture retries still exist; this
build is not a claim that every delay in alpha.96 has been eliminated.

## Fresh correction

A brightness failure blocks the pending handoff; it no longer initiates a
partial-fold native return. This applies equally to direct Home, ordinary-app
and workspace routes, including preparation failure, preparation timeout and
rejected initial brightness writes.

The controller remains in its existing phase with its existing scene, task
placement, rotation ownership and power ownership. It stops the failed brightness
worker and does not retry that preflight, manufacture brightness samples, or
promote an unvalidated primary during the rest of the session. A reversal uses
the existing motion-leg behavior. The six-second app transfer timeout does not
convert this specific blocked preflight into a second mid-fold abort.

There is no new endpoint band or motion tracker. The existing 1.5-second
stillness policy remains the only ordinary partial-fold pause trigger; its
280 ms completed-frame unwind, native readiness checks and 160 ms dissolve
remain. Actual animation endpoints use the existing endpoint cleanup. Returning
to the source endpoint after a reversal cannot rearm the stopped brightness
object. The next fold starts fresh. Android cancellation, lock, disable, thermal,
stale-input, lost-coverage and 30-second overall session bounds still apply.
Non-brightness recovery and the legacy route retain alpha.103 behavior.

The brightness guard exists to require validated physical brightness before a
primary handoff. It is not evidence that the hinge stopped. Keeping its handoff
veto separate from recovery avoids interpreting a missing brightness command as
permission to release rotation/power while the user is folding.

## Validation and limits

`tools/check_live_b8.py` tests the real controller and real pause policy against
fake Android services. Replays cover all three direct routes in both directions,
failed/pending/rejected brightness, motion lasting beyond six seconds, the
reported closing sequence and its opening counterpart, final-degree movement,
reversal back to the source endpoint, failures on later legs, next-fold reset,
true stillness, delayed unwind acknowledgements and termination conditions.
Existing non-brightness recovery tests still exercise the unchanged fallback
method, explicitly injecting that failure independently of brightness preflight.
Brightness, stream, task, scene, power and cleanup suites remain required.
`tools/build_local_test.py` runs a clean build and the full JVM suite, then emits
the APK, committed source archive with Git history, and hash manifest.

No connected SM-F971U is available for optical or device verification. If
brightness validation fails, the destination's native capture/remap remains
blocked: its retained preview may remain until a genuine pause or endpoint.
This change addresses premature brightness-triggered recovery; it does not
repair missing Samsung brightness commands or prove that endpoint blackouts
are eliminated. Those require a fresh handset test of this build.

# Alpha.75 reconstructed local — early remap flashes and Home overhead

VersionCode 1328. Based on alpha.74 commit
56414ac15681dbc140198a6c795c238244a15260. Recovery target remains alpha.20.
This is a reconstructed test build. The user reports visible early flashes on
incoming, outgoing, or both screens in alpha.74. These changes address identified
software contributors; elimination of the observed flashes is not yet verified
on the handset.

## Findings from the supplied alpha.74 report

Four current-build Home sessions show this sequence:

| Session | Both presentations ready | Primary request angle | Request to app readiness | App CPU, one core | Resolution per dimension |
| --- | ---: | ---: | ---: | ---: | ---: |
| 409860704, opening | 396 ms | 21 degrees | 1433 ms | 32.18% | 100% |
| 409864428, closing | 343 ms | 149 degrees | 1374 ms | 28.61% | 25% |
| 409868789, opening | 288 ms | 21 degrees | 1040 ms | 21.99% | 25% |
| 409872323, closing | 290 ms | 152 degrees | 1070 ms | 25.64% | 25% |

Both closing requests occur only about 30 ms after PRESENTATION_READY. Each
request is followed by OFF/ON callbacks as the logical displays exchange physical
panels. In the final close, first presentation callbacks arrive at 409872590/591, the
request is logged at 409872644, D1 reports OFF at 409872671 and ON at 409872709.
These are software callback intervals, not measured optical blackout durations.
They are a strong investigation lead for the user's early-flash observation,
not proof that every flash has the same cause.

The hidden legacy host also processes intermediate mixed metadata: at
409872711 the old inner identity has cover dimensions; at 409872758 the cover
identity arrives. Main-queue delays are 30–46 ms in that interval. The visible
independent scene previously followed mappings only on the controller's 25 ms
poll and checked physical IDs/stacks without validating each panel's dimensions.

Home brightness preparation runs a logcat process over up to 30,000 lines.
Successful preparation can start two physical brightness writes every 8 ms for
two seconds, with extension bounded to four seconds. One opening has an active
hold, one opening has missing samples, and both closings skip pending preparation.
The report does not establish a visual benefit from the hold. It also does not
establish that these writes caused the flashes. Their removal eliminates concrete
work and a potential conflict with native brightness policy.

The 476 ms outgoing moving-gap peak is not reliable evidence of a 476 ms stall:
the direct renderer used the newly arriving target to classify the preceding
interval. It could relabel a stationary wait as moving when the hinge resumed.
Other genuine stalls remain possible. The new measurement uses the previous
submitted frame's unfinished motion.

Home draw guards reject unreported draw state and solid=0 launcher fades before
accepting destination captures. These rejected images are not displayed. Accepted
Home captures retain the composed wallpaper once and have zero launcher-agreement
mismatches in these sessions. Guarded destination captures take 190–261 ms;
source captures take 224–327 ms. Their ownership, alpha, geometry and readiness
checks remain necessary. App CPU excludes shell helpers, SurfaceFlinger and GPU;
the mixed resolutions do not support a controlled performance comparison.

Endpoint coverage removal remains 1–3 ms to submission. The closing power-only
tail still waits for Android cancellation and stable native cover, bounded to
400 ms. Historical ChatGPT OOMs and the camera exception are not Duo crashes and
do not identify the cause of these flashes.

## Changes

- Follow display mapping changes from a narrowly filtered display listener on
  the scene's existing executor. No new thread or faster polling loop is added.
  Retain controller polling if the firmware lacks the executor API. Reject
  mixed physical identity/dimensions/rotation before moving either root. Exchange
  both roots in one transaction and wait for the matching completion. Display
  callbacks cannot extend the controller lease, and cleanup unregisters them.
  SCENE_MAPPING and SCENE_MAPPING_FINAL report listener support, event count,
  submitted exchanges and rejected observations for the next handset test.
- Home consistently leaves brightness to Android. It launches no brightness
  preparation scan, probe or reassertion writer. Ordinary-app and workspace
  brightness behavior remains unchanged. No new delay, fade, static shield or
  endpoint hold is introduced.
- Defer hidden legacy-host geometry/composition work while B8 owns rendering.
  The existing guard updates that host after ownership ends; visible B8 layers
  continue independently. Unknown physical identity remains guarded.
- Configure immutable buffer transform, dataspace, opacity, layer order and
  initial visibility once, in the first real buffer transaction. Subsequent
  frames update pixels and native-edge crop. GPU fences, three-buffer bound,
  presentation acknowledgements and cleanup ownership are retained.
- Correct moving-gap accounting to exclude rest before new movement, while
  retaining gaps during unfinished interpolation.

## Limits and validation

Android's upstream LogicalDisplayMapper explicitly waits for transitioning
displays to be OFF before applying a changed layout. This supports treating the
OFF/ON sequence as an OS transition to investigate; Samsung's implementation and
actual visible pixels on this device remain unverified. An app overlay cannot
guarantee light from a physically powered-off panel. This build does not disable
firmware ColorFade or change the concurrent-display route.

Primary references checked for this investigation:
- https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/display/LogicalDisplayMapper.java
- https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/hardware/display/DisplayManagerGlobal.java

The controller harness passes 724 lifecycle/readiness checks, including Home
preparation callbacks that fail if brightness work starts. The scene harness
passes 36 checks, including event-driven remapping before the next tick, mixed
geometry rejection, older completion after reversal, callback cleanup, owner
lease isolation and unavailable-API fallback. Existing brightness, task, power
and delayed-cleanup harnesses pass. A new JVM sequence distinguishes a 476 ms
idle interval from a real 100 ms unfinished-motion gap. The compiled buffer
harness verifies first-buffer visibility, immutable command reuse, release-fence
ownership, bounded allocation and late-callback cleanup.

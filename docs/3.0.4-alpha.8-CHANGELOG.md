# 3.0.4-alpha.8 — retained custom-wallpaper unlock guard

- Keep the WindowManager-backed custom-photo windows attached alongside the native compositor photo. Previously, native startup removed these windows. The retained windows give the system a photo window to manage during wake/unlock transitions, including while native layers are temporarily obscured.
- Maintain both renderers across display remaps, update both when the photo changes, and remove both when custom wallpaper stops. Keep the existing below-app window type, non-interactive flags, and screen-off retention. No wake lock or screen-power request added.
- Refresh the retained photo windows on screen-on and user-present broadcasts. Accept protected system broadcasts from SystemUI as well as system_server.
- Background reports now record keyguard state, retained window counts, and photo frame commit timestamps beside screen events. Frame commit is not proof of physical visibility.

The alpha.7 handset report showed the native renderer continuously active with two independent wake surfaces and no restart/failure. It did not measure actual photo visibility or capture a user-present event, so it does not establish an exact unlock-to-photo delay. This build targets the missing WindowManager-backed guard; eliminating the flash still requires phone verification.

Fold animation, fade timing, auto-rotate repair and wallpaper bindings are unchanged. Install over alpha.7, test unlocking onto Home on both panels and folding, then copy the background report if a flash remains.

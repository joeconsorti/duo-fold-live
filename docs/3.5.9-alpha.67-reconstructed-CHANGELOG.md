# 3.5.9-alpha.67 reconstructed — incoming system-bar continuity test

During a Duo fold, the incoming panel's application snapshot can lack its status
bar, navigation buttons/gesture handle, or taskbar. Samsung's secondary-display
policy does not guarantee those windows on D1, and Duo's opaque independent
scene roots cover native display layers until release.

This alpha adds a visual continuity path above the incoming glass effect:

- Reuse bounded, drawn system-bar regions from the existing guarded app capture.
  The outgoing screenshot rendering is unchanged.
- While the incoming panel lacks its own bars, fit current-session source-panel
  bar strips to the corresponding incoming edges. Keep strip thickness in physical
  pixels; stretch its long axis. This temporary layout may look different, and
  includes the captured strip background. It is not native destination SystemUI.
- Once incoming native primary readiness succeeds, optionally capture that
  physical panel's own bars. Replace only bar pixels, never the retained app or
  wallpaper. A native region replaces fallback at its edge; other missing edges
  may continue using the source fallback until release.
- Home/workspace isolated snapshots can obtain bar strips through the same
  bounded optional capture path; they do not require wallpaper pixels to be
  reintroduced into app snapshots.
- All bar captures expire with the animation. No cross-session icon/clock cache,
  input interception, new wake lock, system decoration setting, or SystemUI
  registration. Existing handoff gates and cleanup remain in charge.
- At most two optional attempts per physical panel/logical slot, one in flight,
  with retry spacing. Ordinary app source bars need no extra capture. Drawing
  reuses cached crop plans rather than rebuilding them on each animation frame.

Only named, drawn, shown StatusBar/NavigationBar/Taskbar windows with bounded
edge geometry qualify. Expanded notification shades, app windows, full-screen
taskbar windows, missing frame evidence, changed identity/geometry/rotation,
locked screens, and secure-content captures are rejected. Bar absence is not
interpreted as successful capture. Source fallback requires matching rotation.
A taskbar that exists only on the incoming panel cannot appear from a cover
snapshot before native taskbar capture succeeds.

Diagnostics now include `Incoming system bars`, `B8 SYSTEM_BARS`, per-edge
`SOURCE_PANEL_FALLBACK` / `NATIVE_PANEL_SNAPSHOT`, and missing-window evidence.
These are software capture/submission observations, not optical proof. Snapshot
bars are not live buttons; the original native controls take over at release.

Alpha.66 adaptive thermal resolution and saved defaults are preserved. This is
an alpha handset-validation build, not a stable release or a claim of complete
visual continuity.

## Handset validation

Test cover-to-inner and inner-to-cover with a normal app, Home, and a multiwindow
workspace if used. Watch the top time/icons and bottom gesture handle or buttons;
check the inner taskbar specifically. Check quick folds and a mid-fold reversal,
then confirm native controls work after release. Compare at 100% and 25% effect
resolution. Include an immersive app to check that hidden bars are not fabricated.
If a bar disappears, export the diagnostics immediately after that fold, and
identify the direction and missing bar. A screen recording can miss a physical
panel blackout; direct visual observation remains necessary.

## Implementation evidence

The source scene is parentless and uses an opaque guard at layer 2147483646
(`LiveB8Scene`). Lowering that entire scene would also expose other underlying
content; no such z-order change is made. The supplied firmware findings in
`FIRMWARE-DISPLAY-FINDINGS.md` already document the secondary decoration/focus
restrictions and unavailable decoration setter.

The frame parser covers Android's `Frames: parent=… display=… frame=…` output,
as well as the earlier `mFrame` spelling and `mWindowFrames: frame` variants:
https://android.googlesource.com/platform/frameworks/base/+/master/services/core/java/com/android/server/wm/WindowFrames.java

Local verification includes region/geometry/fallback/budget unit tests and the
existing controller, scene, power, brightness, task-routing, Home and workspace
capture harnesses. These cover software behavior only. The packaged build's
manifest identifies the exact commit and artifact hashes. No handset result is
claimed by these tests.

## Capture change

The old app path captured the display, excluding Duo overlays and custom-photo
leaves. Its exact-task HAS_DRAWN checks constrain window state, but do not prove
that the resulting image contains the app. Bright wallpaper also passes the
darkness retry policy. If accepted, that image is retained through remap and can
later receive correct independently captured system bars. This is a plausible
failure mechanism, not a confirmed reconstruction of the user's visible frame.

For ordinary selected-app captures (operation 5), the existing pre-capture
window dump now resolves the selected task's visible window owner UID and
window identities. CaptureArgs.setUid restricts the existing screenshot to that
owner. The existing exclusion list still removes Duo's own rendering and photo
layers, including when Duo itself is the selected app. The existing post-capture
dump must contain the same owner and visible windows. Recreated windows,
ambiguous or unavailable owners, current DRAW_PENDING masked by historical
HAS_DRAWN, explicit zero/nonfinite shown alpha, and empty-alpha center samples
are rejected. Opaque black content is not rejected by the alpha check.

Missing owner-filter API support fails closed and is reported; there is no
automatic unfiltered screenshot substitution. Existing retry and controller
cleanup bounds remain. A failure retains the previous app presentation while
the controller resolves or ends the transition. No new screenshot, metadata
poll, fixed delay, readiness hold or endpoint hold is added. The native reveal
checks are unchanged. Rejected copied bitmaps are released even if the second
window dump throws, closing an existing failure-path allocation leak.

This is owner filtering, not exact task-layer isolation: shared-owner surfaces
may remain, and firmware behavior requires handset validation. Other visible
tasks are still rejected. This does not override secure/protected capture flags.
Home, workspace, legacy display captures and composition diagnostics retain
their respective capture paths. No wallpaper file is decoded or changed.

Filtered app frames do not claim to contain SystemUI bar pixels. Destination
bars continue through the existing independent optional capture and base-effect
composition. The cached comparison mode can populate its cache from independent
bar captures, but no longer extracts bars from owner-filtered app images.

The report now retains bounded metadata for eight recent sessions, up to twelve
entries each, including source and destination provenance, capture decisions,
failures, final bar-work summary and renderer timing. No extra pixel captures,
disk writes or periodic work are introduced by this history.

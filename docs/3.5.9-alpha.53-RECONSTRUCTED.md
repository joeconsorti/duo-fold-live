## Cause addressed and Home-only changes

The old custom-wallpaper Home path captures the entire primary display during
the launcher transition. Window HAS_DRAWN and window alpha cannot establish
individual icon opacity. Its dark-pixel gate accepts a bright wallpaper even if
the launcher has almost disappeared, and the accepted image is then retained.
That mechanism is consistent with the video; the specific Samsung layer causing
the initial fade is not proven.

Custom-wallpaper Home now uses the public API 34+ takeScreenshotOfWindow operation
for the focused launcher window. The existing wallpaper UiAutomation connection
resolves only the focused default-Home window ID/package/bounds. It does not
launch, move, change focus, reparent or hide any window. The enabled accessibility
service performs the screenshot, requiring canTakeScreenshot=true in its metadata.
The privacy disclosure describes this narrow capture path. Node-text retrieval
remains disabled for the service; the existing UiAutomation reads package identity.

Shell-side checks before and after capture require unlocked fullscreen Home,
the selected task window HAS_DRAWN, no explicit window fade/exit, and the expected
physical primary display ON with matching dimensions/rotation. The window ID and
bounds must also remain unchanged. Secure/failed/late captures are not accepted.
Hardware buffers and unpublished pixels are released on rejection or timeout.
Only one capture is in flight; attempts are at least 350ms apart.

The launcher window is composited over the selected panel's saved wallpaper,
drawn once behind it. No captured display wallpaper/overlay is added above icons,
and no opacity is artificially boosted. An alpha-content heuristic rejects
obviously faded launcher pixels and severe content loss relative to the outgoing
Home. The previous valid image is retained while the existing controller retries.
Rejected content never passes merely because a timeout elapsed. This heuristic
does not establish that every icon exists, and cannot detect all fading inside
an opaque launcher background. Different icon/widget layouts may affect coverage.

The temporary cover-to-inner Home projection now preserves the complete cover
image at contained scale on the right, avoiding alpha52's large fill/crop. This
is a temporary source layout until native inner Home is captured, not a fabricated
destination layout. Backdrop clipping and glass sampling use the same transform.
The inner-to-cover Home projection still fills the cover. Native same-panel
layout is unchanged.

Armed Home inner diagnostics additionally save the accepted isolated launcher
thumbnail with transparency, alongside the retained composite and physical inner
sequence. The offline viewer labels these three images and uses a checkerboard
behind the launcher. Alpha counts and rejected-capture reasons appear in reports.
Existing inner-only sampling, byte/time budgets, one-flight limit and post-cleanup
tail remain. These sequential captures are not synchronized or optical proof.

## App-path preservation

Only homeScene plus enabled custom wallpaper selects the new capture route.
Ordinary apps still call GlassFrames.incoming with their existing exclusions,
dark-content gate and parameters. No controller/task move, readiness interval,
power request, brightness, rotation, endpoint release, shader source or moving
buffer lifecycle is changed. The new projection is guarded by homeScene.
Home without custom wallpaper retains its prior capture route. Recents routing
is unchanged; this patch does not turn it into an ordinary-app task transfer.

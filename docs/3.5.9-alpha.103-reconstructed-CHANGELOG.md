# Alpha.103 reconstructed local — Duo refresh and partial-fold recovery

VersionCode 1356. Based on alpha.102 commit 13edb951999932e2de5f00f533e688eef32518f0.

## Report evidence

In current alpha.102 closing session 2738263, both presentations exist by
2738501 but brightness preparation fails at 2740317, after 2054 ms. The reader
reports `Recent brightness snapshot timed out (tail=512)`. The angle is about
42 degrees. Software recovery cancels concurrent ownership at 2740320–2740323;
Samsung's base/current state becomes OPENED, not the desired below-90 cover.
The controller verifies the inner screen and observes the cover OFF at 2740669.
At 2740732 the angle is 35 degrees. Cleanup finishes around 2740905, before a
later 17–24 degree hold. With no controller session, the pause gesture cannot
correct that panel. The cover returns only at actual closure around 2743822.
These are software observations; the reported blackout comes from the user.
Historical alpha.101 processes are not treated as current alpha.102 evidence.

Alpha.102's smaller finite log dump did not fix this. Current session rates are
about 58 submitted FPS on inner and 56 on cover, consistent with the old 17 ms
pacing and 60 Hz request. They are not measured optical/panel rates.

## Changes

- Duo's direct buffers now schedule via Choreographer, coalescing requests to a
  display-vsync callback as Live does. Window-backed rendering uses animation
  callbacks too. Remove the 17 ms limiter and request the highest supported
  rate at the current physical resolution, capped at 120 Hz, on the actual
  buffer layer. Switches are seamless-only. Two-in-flight and three-buffer
  bounds, release fences and existing thermal protections remain. No new
  thermal FPS throttle is introduced. The system/GPU can still deliver less
  than 120 FPS; session submission/callback counters remain the evidence.
- One short-lived logcat stream serves the entire brightness preparation.
  It follows from one tail record and rejects commands older than preparation.
  Complete, drained records can be consumed while the process remains alive;
  no retry depends on dump exit. Initial observation is at most 150 ms; each
  restoration observation remains bounded to 400 ms and waits for new data.
  The existing 1200 ms restoration window, per-panel post-clear timestamps,
  valid positive SDR checks and one-time probe remain. OFF commands veto old
  positives. Split/oversized records, process loss and cancellation fail closed.
  Child lifetime is bounded to six seconds and preparation/cleanup terminates
  it. AOSP logcat's nonblocking path documents a two-second socket timeout;
  that is relevant to this design, not proof of the handset's precise delay.
- App-side failures with retained coverage now reuse the pause-return path:
  select cover below 90, inner above 90, active at exactly 90; restore the task;
  finish the 280 ms committed-frame unwind and 160 ms dissolve only after
  native readiness. Preserve the selected native panel after removing images,
  even if the normal 1.5-second stationary gesture had not yet fired. Crossing
  90 continues on the other native panel without restarting animation. At an
  endpoint the next leg becomes eligible. Crossing during unwind cannot extend
  the original 1800 ms recovery budget. No guessed brightness writer is started.
- Android cancellation is separate: never reacquire a canceled request. Recheck
  eligibility after restoration calls, and prevent fresh partial-angle replies
  from immediately restarting a canceled software-return episode. Lock,
  disconnect/stale input, disable, severe thermal status and endpoint cleanup
  remain in force. No changes to Home/workspace fallback semantics.

## Validation and limits

Run `python tools/check_live_b8.py` with JDK 17. Deterministic real-controller
replays cover both origins and both sides of 90, exactly 90, the reported
42-to-35 closing case with OPENED base state, extended holds, midpoint crossing,
blocked native readiness, delayed renderer unwind, timeout, Android cancellation
(including during task restoration), lock, disable, thermal and stale input.
Brightness tests cover fresh post-clear validation, cached-only writes, latest
OFF veto, out-of-order and split commands, cancellation and malformed output.
The stream is tested against both controlled children and a real running process
that emits commands without exiting. Existing scene, task, power, fence/pipeline
and cleanup tests remain required. `tools/build_local_test.py` reruns the full
JVM suite and packages APK, committed source history, and a hash manifest.

No connected SM-F971U or optical measurement is available here. This changes
both the preparation failure and its incorrect panel recovery; it does not
establish that all Samsung remap blanking is gone. If native readiness cannot
be established within the fixed recovery budget, coverage/ownership is released
rather than retaining an opaque frozen image indefinitely. Check app folding,
paused closing near 35, pauses above 90, and normal endpoints on the handset.

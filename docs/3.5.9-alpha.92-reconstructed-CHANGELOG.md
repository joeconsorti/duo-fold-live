# Alpha.92 · Outgoing flash during app handoff

This test follows the Fold Power Lab B8 brightness experiment. In the earlier handset tests a YouTube transfer passed and ChatGPT flashed on one run and passed on another. The brightness command intervals varied between runs. A separate flash-free round trip used fixed display mapping. Alpha.92 retains alpha.91's native mapping and tests the physical brightness hold during ordinary app transfers.

Alpha.91 wrote the two physical tokens in enumeration order. A rejection on either token could terminate the worker for both. Alpha.92 services the identified outgoing physical token first. For the first 320 ms of the existing hold it also attempts one outgoing-only write between regular paired writes, up to 80 extra attempts. It uses the same validated positive brightness as the original writer. Both panels must accept the first writes before the switch. Once armed, a false return or transient display-state exception on one panel leaves the other panel eligible, and the next scheduled write can recover. The existing lease, hard timeout, release and cleanup bound all writes.

## Handset check

Use the ordinary app where the flash repeats. Close it from the inner screen, then unfold it from the cover. Copy the status after the pair. OUTGOING_FLASH_HOLD identifies the source panel, accepted and rejected commands, first rejection and recovery timestamps, and the maximum interval between accepted calls on each panel. Compare these with POWER_INTERVAL and the physical IDs on FLASH_FRAME_WAIT and FLASH_FRAME_RESUMED. Frame callbacks and API acceptance are software observations. The 206 ms between OFF and ON samples in the alpha.91 report was not an optical measurement. If needed, the existing “Arm next 6 folds” control can include composition samples in a diagnostic ZIP.

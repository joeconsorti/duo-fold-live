## Evidence from the alpha.71 Home report

The user reports a translucent-looking incoming body on every Home fold/unfold,
with clear status/task bars; one close also affected the outgoing body and left
the cover dark until reopening. No camera recording or composition pixels were
provided for this test. Custom wallpaper was disabled and its host was stopped.
Home captures explicitly used whole-display operation 9, unlike the owner-filtered
ordinary-app operation 5 fixed in alpha.71.

Whole-display Home pixels can bake transition/dim layers or faded launcher child
views into an otherwise opaque image. HAS_DRAWN, whole-window alpha and a bright
wallpaper do not establish icon opacity. The accepted frame is then retained for
the fold. Independently captured destination bars can remain clear. This is a
concrete capture-path gap consistent with the report; the exact Samsung layer
that produced the observed washout is not proven. The successful sessions' Home
preview veil had reached zero, so a persistent cosmetic preview is not supported
by those final software samples. The disabled retained photo is not evidence of
an active photo overlay.

The failed close is session 402017174:

- Brightness preparation failed at 402019220 after 1888 ms; the handoff gate had
  been waiting since 402017767 (1453 ms).
- Native fallback occurred before a cover-primary request. Recovery verified
  the inner panel and released coverage with endpointSeen=false.
- Cover D1 reported OFF at 402019583. Full close arrived at 402020901. Fold sleep
  reason 13 was verified at 402020967 and the wake call returned at 402020970.
- No cover ON event follows until 402023368, when the device starts opening again.

Two other Home closes also recorded fold sleep despite the stay-awake setting.
The recovery dispatch was 0–1 ms, so slow helper preparation is not the explanation.
The cover OFF-to-ON callback spans on those closes were 158 and 324 ms. These are
software callback intervals, not optical blackout measurements. Endpoint coverage
removal was submitted in 1 ms; that did not establish sustained display power.
Sampled thermal status was zero. The old ChatGPT crash buffer is unrelated evidence.

## Changes

Native Home with custom wallpaper disabled now captures two verified owners:
the current selected launcher and the visible native wallpaper. Both requests
use the same geometry and Duo exclusions and are submitted before waiting, with
one shared 250 ms callback budget. Existing Home/task/window/physical mapping
guards still run before and after. Wallpaper identity must remain stable; missing,
ambiguous or launcher-shared wallpaper ownership rejects the image. No unfiltered
display fallback or retained custom photo is substituted.

The launcher alpha heuristic runs before compositing, with the outgoing launcher
sample as the missing-content reference. Obviously faded or severely depleted
images retain previous valid coverage and retry under existing bounds. Native
wallpaper is drawn once below launcher-owned pixels onto an opaque body; launcher
alpha is not boosted. This is owner isolation, not task/subtree isolation, and
cannot detect every fade inside opaque launcher content. Shared wallpaper-owner
SystemUI layers may exist in the background image; they cannot be placed over
the separately captured launcher by this compositor. The independent destination
bar path remains unchanged. Ordinary apps, workspaces, custom-wallpaper Home,
saved glass controls and shader behavior keep their existing routes.

Home brightness preparation is now passive and optional. It reads existing
physical commands once with a 400 ms worker budget and never performs a temporary
brightness nudge or restoration retry. If validated samples are already ready at
handoff, the existing bounded hold can use them. Missing, pending or failed samples
are discarded without blocking native remap or aborting Home. No guessed brightness
is written. Ordinary-app and workspace brightness policy is unchanged.

At a closed Home endpoint with the cover already primary, coverage is revoked
immediately. Existing power ownership may remain for at most 400 ms while Android
cancels its concurrent-state request. It releases sooner after cancellation and
100 ms of stable native cover mapping. This avoids issuing an explicit cancel
ahead of native close policy. No screenshots, brightness writes, power renewals
or new state requests run in this tail. New movement, disable, lock/noninteractive,
stale input or severe thermal state releases it through normal cleanup. Opening
and wrong-panel fallback still release immediately. This is a targeted mitigation
for the observed release ordering, not proof of a Samsung power-policy root cause
or a guarantee against optical blackouts.

## Latency and verification

There is no new settling timer on the image path. Native Home now performs two
filtered captures instead of one whole-display capture, so capture/GPU work may
increase even though requests overlap. The report records pairMs and guardedTotalMs
for source and destination frames; a handset comparison is required to quantify
that cost. The Home brightness gate responsible for the 1453 ms wait is removed.
The power tail follows coverage removal and does not retain a screenshot over Home.

Validation: 645 JVM tests in the initial Android unit run. The clean delivery build
reruns the complete suite. Real controller harness: 724 checks, including optional
brightness failure, immediate coverage revocation, OS cancellation, missing callback
bound, reversal, lock and disable. Brightness harness: 34 checks including no probe,
no retry/sleep and no guessed samples in passive mode. Native Home CPU compositor:
4124 pixel/alpha/ownership checks; paired capture harness: 80 request ordering,
exclusion, failure, secure-result, timeout/late-callback and buffer-cleanup checks.
Existing destination-bar CPU oracle: 1131 checks. Home-window and window-priority
harnesses also pass. Fake framework/pixels do not establish handset appearance.
